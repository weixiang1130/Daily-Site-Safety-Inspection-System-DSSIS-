# 地端戰情室

## 為什麼要搬

戰情室原本和填報系統一起放在雲端，但它是**大螢幕整天開著、每分鐘更新**的東西：
監視畫面、環境數據、人數，每一次更新都是一次雲端函式呼叫。填報一天幾十次，
戰情室一天幾萬次——額度幾乎都花在牆上那一面，而不是真正的業務。

更關鍵的是，戰情室要的資料**來源本來就都在公司網路內**：

| 資料 | 來源 | 雲端取得的困難 |
|------|------|----------------|
| 監視畫面 | 工地 NVR | 主機限制來源 IP，雲端第一次請求就被回 403，而雲端沒有固定對外 IP 可加白名單 |
| 進出場人次 | 公司門禁資料庫 | 內部資料庫不對外開放 |
| 環境數據 | 廠商氣象站平台 | 可從外部取得，但沒有理由繞一圈 |

為了讓雲端看得到監視畫面，原本得在公司內網另外跑一支推送程式，把畫面傳到
雲端儲存區再讓瀏覽器讀回來——同一張圖片在網路上來回兩趟。搬到地端之後，
這一整條路（推送程式、儲存區、權杖驗證）都不需要了。

## 搬完之後的樣子

```
工地手機 ──填報──> 雲端（Netlify）
                      │
                      │ sync_forms 定時拉取（只拉統計要用的欄位）
                      ▼
     公司內網  ┌─── 地端伺服器（FastAPI + SQL Server）───┐
               │                                        │
   NVR ────────┤  collectors/    app/                    │
   門禁資料庫 ─┤   weather        /api/dashboard         │──> 戰情室大螢幕
   氣象站平台 ─┤   access         /api/cctv/snapshot     │
               │   sync_forms                            │
               └────────────────────────────────────────┘
```

**填報留在雲端**——工地是拿手機在現場填，必須從外網進得來。
**戰情室在地端**——資料來源都在內網，而且不再吃雲端額度。

雲端就算暫時連不上，牆上仍看得到最後一次同步的內容。

## 安裝

### 1. 設定檔

複製 `.env.onprem.example` 成 `.env.onprem`，填入實際值。

> `.env.onprem` 含資料庫、監視器與氣象站的帳號密碼，已被 `.gitignore` 排除，
> **不可進版控**。本 repo 為公開。

### 2. 套件

```bash
cd backend/onprem
pip install -r requirements.txt
pip install -r requirements-mssql.txt   # 用 SQL Server 時
pip install pyodbc                      # 讀門禁資料庫用
```

### 3. 啟動 API

```bash
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

大螢幕開 `http://<地端主機>:8000/static/dashboard.html`。

`PUBLIC_DASHBOARD=true` 可讓大螢幕免登入（放在公司內網才適用）。
**這台機器不要對外網開放**，否則等於把全公司的缺失資料公開。

### 4. 設定工作排程器（伺服器與收集程式）

`backend/scripts/` 內有現成的啟動腳本（相對路徑，換機器免改）。以系統管理的
PowerShell 註冊六個排程：

| 排程 | 腳本 | 頻率 |
|---|---|---|
| SafetyOps-Server | run_server.cmd | 登入時啟動，當機自動重啟 |
| SafetyOps-Weather | run_weather.cmd | 每 15 分鐘 |
| SafetyOps-Access | run_access.cmd | 每 30 分鐘（防火牆開通後自動生效） |
| SafetyOps-Sync-AM／PM | run_sync_forms.cmd | 每日 07:00、19:00 |
| SafetyOps-Finops | run_finops.cmd | 每日 07:15（FINOPS_PWD 填入後生效） |

均為「單次觸發、跑完就結束」而非常駐迴圈——長駐程式睡著或當掉不會有人
發現，單次觸發每次都是乾淨的一輪，下次何時跑由排程器保證。
所有排程經 `run_hidden.vbs` 以隱藏視窗執行——桌面不會彈出黑色主控台，
也就不會被順手關掉（實際發生過：伺服器的視窗被關，牆面斷線，
排程結果碼 0xC000013A）。停止伺服器請用工作管理員結束 python，
或 `Unregister-ScheduledTask -TaskName "SafetyOps-*"` 整組移除。
記錄寫到 `logs/`（不進版控）。

**筆電注意**：排程設定已允許電池供電執行，但**闔上蓋子進入睡眠時一切暫停**。
臨時當主機時請把「闔上螢幕時」設為不採取動作，或改用正式主機。

首次同步請先跑一次 `python -m collectors.sync_forms --full`，把既有資料全部拉回來。

## 讓工地電腦看到儀表板

**正規做法是「工地檢視器」——完全自足的免安裝包（本機 SQLite＋自帶收集程式），見
[docs/工地檢視器.md](工地檢視器.md)。** 本節的雲端看板是它的**備援**：
只在工地連外網也出問題、或檢視器暫時無法交付時啟用，
開關是 `.env.onprem` 的 `WALL_ENABLED`（預設關閉，關閉時推送程式
與安裝腳本的排程都不會動作）。

備援存在的理由：檢視器交付前的過渡期，工地還是得有東西可看，
而雲端看板只要一個網址就能動。

以下是備援的原理與設定。

工地辦公室的電腦有兩個限制：

1. **連不到公司內網**——進不去內部 NAS，也連不到內網資料庫主機的 1433 埠（實測不通）
2. **不能安裝需要管理員權限的軟體**

在網路放行前，伺服器不能放在工地也搆不到內網，只剩公網一條路。
地端負責算，雲端只當一面看板。

之所以是「地端算」而不是「雲端自己查」，因為六個資料源裡有兩個只有公司
內網拿得到，而雲端函式進不了公司內網：

| 儀表板上的東西 | 資料來源在哪 | 更新頻率 |
|---|---|---|
| 缺失、照片、簽名 | Netlify 填報站 | 12 小時 |
| 在場／進出人數 | 人臉辨識裝置（公網 IP） | 5 分 |
| 溫濕度／PM／噪音／熱危害 | 氣象站廠商平台 | 15 分 |
| 工程進度（實際 vs 預估） | FinOps 資料庫（**公司內網**） | 月結 |
| 今日重點工項 | NAS 上的七合一列控表（**公司內網**） | 改版時 |
| 門禁人次 | 門禁資料庫（內網，未通） | 已由人臉裝置取代 |

所以地端主機仍必須是一台**在公司內網、且連得到網際網路**的機器。

### 做法：地端推快照 → 雲端當看板

```
公司內網的地端主機                    Netlify                 工地電腦
──────────────────                 ─────────────            ──────────
collectors 抓五個來源
      ↓
  SafetyOps DB
      ↓
  本機 /api/dashboard
      ↓  每 5 分鐘 POST 一份快照
                    ─────────→  Blobs 存快照
                                /api/wallboard 讀出   ←──  開網址就看到
```

這與早期「推監視畫面上雲」的做法是同一個模式：由地端主動往外送，
地端不需要對外開任何埠，工地電腦只負責開網址。

**關鍵限制：只寫 Blob，絕不觸發重新部署。** 每 5 分鐘 deploy 一次會在三天內
燒光免費的 300 分鐘建置額度；寫 Blob 只算一次函式呼叫。看板端讀取節奏與推送一致
（每 5 分鐘），讀得更勤只是對同一份快照白繳函式呼叫。

### 設定

**地端**（`.env.onprem`）：

```ini
CLOUD_API_URL=https://<你的站台>.netlify.app
CLOUD_SYNC_TOKEN=<與雲端 SITE_AGENT_TOKEN 相同>
WALL_DAYS=30
WALL_INTERVAL=300
```

排程加一支（`backend/scripts/run_push_wallboard.cmd`，5 分鐘一次）。

**雲端**（Netlify 環境變數）：

| 變數 | 說明 |
|---|---|
| `WALL_TOKEN` | **必填**。看板權杖，長隨機字串。未設定時 `/api/wallboard` 一律回 503，看板不會啟用 |
| `SITE_AGENT_TOKEN` | 已存在（地端同步用），推快照沿用同一組 |

**工地電腦**：瀏覽器開這個網址，存成書籤或設為開機首頁即可。

```
https://<你的站台>.netlify.app/static/dashboard.html?k=<WALL_TOKEN>
```

### 看板模式與地端有什麼不同

帶了 `?k=` 就進入看板模式：

- **一次讀回全部**（品牌、工地、儀表板），不做任何需要登入的呼叫
- **隱藏工地與天數下拉**——快照是固定視圖，範圍在地端產生時就決定了，
  留著只會讓人按了以為壞掉。「回首頁」同樣隱藏：首頁要登入，工地沒有帳號
- **不顯示監視格**。CCTV 是即時代理到工地攝影機的，雲端連不到。這裡讓整格
  不出現，而不是擺一個永遠寫著「看不到」的方框——牆上位置很貴

### 資安：這條路真正的代價

缺失描述、廠商名稱與工地位置會從「公司內網」搬到**公開網際網路**。地端設
`PUBLIC_DASHBOARD=true`（拿到網址就看得到）在內網是安全的，同樣的設定放到
Netlify 上意義完全不同。因此看板以 `WALL_TOKEN` 驗證，**權杖外流時改一次
環境變數即可撤換**，不影響既有的登入機制。

權杖等同於資料本身，管理方式比照密碼：不寫進文件、不貼進聊天室、不進版控。

### 門禁人數尚未驗證

撰寫當下開發用的筆電連不到資料庫網段的 1433 埠：主機 ping 得到、DNS 也解析得到，
但 TCP 不通，應是網段之間的防火牆規則。因此**檢視表的欄位結構還沒實地看過**。

`collectors/access.py` 因此不寫死欄位名稱，而是連上之後看實際有哪些欄位再對應；
對應不到就不寫入任何資料並印出實際欄位。寧可牆上顯示「尚無資料」，也不要掛一個
猜出來的數字上去——疏散時有人會照著那個數字點名。

在地端主機上先跑一次確認結構（會遮蔽姓名與證號）：

```bash
python backend/tools/inspect_access_view.py
```

若自動對應挑錯了，用 `ACCESS_COL_*` 指定正確欄位，見 `.env.onprem.example`。

## 個資

門禁資料含姓名與員工編號，屬第三人個資。`collectors/access.py`
**只寫入彙總後的人數**，不把任何個人欄位存進本系統的資料庫，也不寫進記錄檔。
