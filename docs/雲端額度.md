# 雲端額度

2026-09-03 站台額度用盡，整站回 `503 usage_exceeded`——工地連填報都打不開。
這份文件記錄**實際**的消耗結構，以及為什麼一開始的判斷是錯的。

## Netlify 是 credits 計費，不是「函式呼叫次數」

這點最先搞錯：我們一度按「免費 125,000 次函式呼叫」在算，於是拚命降低
輪詢頻率。實際是 credits 制（官方費率，2025-09 起的新方案）：

| 項目 | 費率 | 對我們的意義 |
|---|---|---|
| **Production deploys** | **15 credits／次** | **免費方案等於每月最多 20 次部署** |
| Database compute | 10 credits／GB-小時 | 重點是「資料庫醒著幾小時」，不是查了幾筆 |
| Functions compute | 10 credits／GB-小時 | 穩態約 2／月，可忽略 |
| Web bandwidth | 20 credits／GB | 穩態約 8／月 |
| Web requests | 2 credits／萬次 | 穩態不到 1／月——先前拚命優化的就是這項 |
| **Deploy previews／branch deploys** | **免費（不計量）** | 開發測試的正確去處 |

免費方案 **300 credits／月，硬上限**（用完整站停止服務，就是 9/3 發生的事）；
Personal 方案 $9／月 1,000 credits；Pro $20／月起 3,000 credits。

也就是說：**消耗額度的是「我們部署了幾次」與「資料庫醒著多久」，
不是「工地用了多少」。**

用量對照（實測）：

```
Jun 19 – Jul 18    301 credits
Jul 19 – Aug 18    1K credits
Aug 19 – Sep 18    1.5K credits（9/3 就用完）
```

高峰日與當天的 commit 數完全對得上：8/17 十二個、8/19 六個、8/24 七個。

事後結算 1.5K 的來源：8 月步調的部署（40+ 次 × 15 = 600+），加上故障
檢視器每 13 秒打一次雲端、讓資料庫**全天不休眠**——DB compute 以醒著的
時數計費，24 小時 × 0.5 GB × 10 = 一天約 120 credits，一台失控機器一個月
可以燒 3,600。兩者相加，半個計費週期燒完 1.5K 完全合理。

## 因此，省額度的優先順序

### 1. 減少部署次數（影響最大）

**自動的一半**：`netlify.toml` 的 `ignore` 規則，只有 `frontend/`、
`backend/cloud/`、`netlify/`、`netlify.toml`、`package.json` 有變才建置。
這個 repo 有兩成的 commit 只動地端、工具或文件，對雲端毫無影響，
以前卻照樣觸發完整部署。

```toml
ignore = "git diff --quiet $CACHED_COMMIT_REF $COMMIT_REF -- frontend backend/cloud netlify netlify.toml package.json"
```

（`git diff --quiet` 無差異時回傳 0，而 Netlify 規定 ignore 回傳 0 就跳過
建置，語意剛好吻合。取不到 CACHED_COMMIT_REF 時回非 0 → 照常建置，
失敗方向是安全的。）

**需要改習慣的另一半**：剩下八成的 commit 確實動到雲端程式碼，但**不必
每改一點就推一次**。累積成一次再推——十個 commit 一起推是一次部署（15
credits），分十次推就是十次（150）。開發期間這是最大的浪費來源。

**開發測試走 branch deploy（免費）**：deploy previews 與 branch deploys
不計 credits。要在雲端上驗證改動時，推到開發分支看 branch deploy，
確認沒問題再一批合回 main——只有合回 main 的那一次要付 15 credits。
目標：正式部署每月 8 次以內（120 credits）。

### 2. Database compute（10 credits／GB-小時）

計費單位是「資料庫醒著的時間」，不是查詢筆數。閒置幾分鐘會自動休眠，
所以重點只有一個：**別讓任何東西定期去戳它**。

- 看板的推送與讀取都走 Blob，不碰 DB ✓
- `/api/v1/export` 是最重的查詢，一天只跑 2 次 ✓
- 任何比休眠門檻更密的輪詢（例如故障迴圈的每 13 秒一次）會讓 DB
  **永遠醒著**：一天 120 credits，一台失控機器就超過整月免費額度十倍
- 開發時反覆打 `/api/health`（三個 COUNT）同樣會把它叫醒，別當 ping 用

`collectors/cloud_budget.py` 的每日上限就是為此而設：失控時最多打完
當日額度就停，DB 醒不到一小時。

### 3. Web requests（幾乎可以忽略）

穩態約 4,400 次／月＝**不到 1 credit**。相關設計仍然保留，因為它們同時也在保護
database compute：

- 推送、前端輪詢、雲端快取三者對齊 **15 分鐘**（不一致的話，多出來的
  讀取都是對同一份內容重複付費；對齊後多面牆共用 CDN，回源不隨螢幕數增加）
- 內容沒變就不推（比對指紋，排除每次必變的 `generated_at`）
- 只在 `WALL_HOURS`（預設 6-20 時）推送

## 免費方案（300 credits）的月預算

| 項目 | credits |
|---|---|
| 正式部署 8 次 | 120 |
| Database compute（穩態，每日醒約 1 小時） | ~150 |
| Web bandwidth | 8 |
| Functions compute | 2 |
| Web requests | <1 |
| **合計** | **~280／300（94%）** |

**結論：免費方案撐得住，但沒有犯錯空間**——多部署幾次、或資料庫多醒
幾小時就爆。其中 DB compute 那項是估計值（醒著的時數難精準預估），
實際可能更低也可能更高。若這套系統已是正式營運工具，Personal 方案
$9／月（1,000 credits）能把「部署紀律」從生存問題降級成節約習慣。

## 每日硬上限：防止再次歸零

`backend/onprem/collectors/cloud_budget.py` 給每台機器一個每日上限
（`CLOUD_DAILY_BUDGET`，預設 300）。**計數寫在磁碟，重啟繞不過去。**

這道保護的必要性與計費模型無關：工地檢視器的啟動檔在程式當掉後每 10 秒
重啟一次，而同步程式在每次啟動時無條件呼叫一次雲端——每 13 秒一次的
迴圈會把 web requests 與 database compute 一起拖下水，而我們要等到站台
掛掉才會發現。

實測：模擬 1000 次失控呼叫只放行 5 次；「重啟」後放行 0 次。

## 站台被停用時怎麼辦

`503 usage_exceeded` 代表額度用盡，**整站停止服務**（連不碰資料庫的
`/api/branding` 也一樣）。確認方式：

```bash
curl -s https://<站台>/api/health
```

恢復途徑只有兩條：等計費週期重置，或升級方案（免費方案是硬上限、
沒有加購選項；Personal $9／月 1,000 credits 是最小的升級）。地端戰情室與工地檢視器
在這期間仍可正常運作——它們的資料來源不經過雲端，只有「表單同步」會暫停。
