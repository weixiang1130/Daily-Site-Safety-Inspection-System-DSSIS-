# 出工資料庫

工務所 LINE 群組「出工回報」的歷史明細，存在雲端資料庫，供人力與工種分析。

## 為什麼要存

工地看板只顯示「今天」。出工歷史原本只存在來源試算表（LINE → Google 試算表）
裡——它曾被移到垃圾桶；若被截斷、換表或刪除，歷史就沒了。這個資料庫是出工
歷史的正本：**來源裡消失的列不會被刪除**。

## 資料流

```
LINE 群組 → Google 試算表
   ↓ GitHub Actions 每天 00:07（台北）
   ↓ backend/cloud-runner/push_worklog.py
   ↓   解析：collectors/worklog.py 的 collect_reports()（與看板共用）
   ↓ POST /api/v1/ingest/worklog（權杖 WALL_INGEST_TOKEN）
雲端資料庫 worklog_* 表
   ↓ 登入後 /static/worklog.html 下載 CSV
Excel／Power BI 分析
```

每晚重送**最近 14 天**：事後修改的回報會被更新，某晚沒跑到由隔晚補上。

## 資料表（netlify/database/migrations/008_worklog）

| 表 | 一列是什麼 | 重點欄位 |
|---|---|---|
| `worklog_reports` | 一家廠商、一棟、一天 | 日期、棟別、廠商、**總人數**、工種摘要、作業主管、施作項目、回報人、回報時間、原文 |
| `worklog_trades` | 一筆回報中的一個工種 | 工種（原寫法）、人數 |
| `worklog_trade_aliases` | 工種寫法 → 歸類 | 由人維護 |
| `worklog_rejects` | 解析失敗的一則訊息 | 原文，供人工檢查 |

同一天同一棟同一廠商以最新一則為準（廠商常重發更正版）。同一則訊息因解析
規則改進而改判到不同廠商時，舊的那筆會被刪掉、不會重複。

## 分析時一定要知道的事

- **總人數看 `worklog_reports`，工種結構看 `worklog_trades`。** 兩者不可混用：
  - 只有訊息逐項寫了人數（「電班*8」「鋼筋工：17」）才有工種明細。實測約
    **四成**回報有，其餘只寫總人數。
  - 有工種明細的回報中，約一半的**工種加總 ≠ 總人數**（總人數常含工程師，
    或只列部分工種）。
- **工種寫法不一致**：電班／電工班、電焊工／電銲工、水班／水工班、監火員／
  監火工、消防／消防水／消防水班。到出工資料庫頁的「工種歸類」統一。
- **有些「工種」其實是作業項目**：「B區版筋綁紮」「柱筋缺失改善」「十輪車內運」
  是該作業分派的人數。建議歸成「（作業分派）」，分析工種時排除。
- **機具不算人**：塔吊、堆高機、挖土機型號（PC120）等在解析時排除。若發現新的
  機具被當成工種，把關鍵字加進 `collectors/worklog.py` 的 `MACHINE_WORDS`，
  再手動推送一次全部歷史重算。
- 未填棟別的回報，棟別為空字串。

## 首次建庫與重算

合併上線後，到 GitHub → Actions → 工地看板外部區塊 → **Run workflow**，勾選
「出工資料庫：推送試算表內全部歷史」後執行。解析規則改版後也用同一方式重算
（以 upsert 寫入，不會重複）。

本機驗證（不推送，只印摘要）：

```bash
python backend/cloud-runner/push_worklog.py --dry-run
```

## 成本

雲端資料庫按「醒著的時數」計費（見 docs/雲端額度.md）。寫入每天只在 00:07
一次，這個時段看板每日第一次讀取本來就會喚醒資料庫，通常不增加喚醒；最壞
約每月 +12 credits。在出工資料庫頁查看或下載也會喚醒資料庫，屬低頻手動操作。

## 個資

資料含廠商、作業主管、回報人（LINE 顯示名稱）與訊息原文。只能登入後由管理員、
主管、職安人員下載；工種歸類限管理員與主管修改。不存 LINE 使用者 ID。
**資料絕不可放進 repo**（公開 repo）。

## 驗證紀錄
