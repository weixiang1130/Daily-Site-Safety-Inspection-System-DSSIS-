# 工地看板：雲端排程（不再依賴地端主機）

## 問題

工地看板（dashboard.html 五區塊）原本靠**地端主機**每 15 分鐘把整份快照
推上雲端 Blob。地端跑在誰的電腦上，那台電腦一關、睡著或重開，雲端看板
就顯示「資料已停止更新」——實際上就發生過（最後更新停在兩天前）。

看板不該綁在任何一台特定電腦上。

## 關鍵發現：這塊看板的資料源其實都在公司網路外

| 區塊 | 資料源 | 需要內網嗎 |
|---|---|---|
| 環境（微型氣象站） | 廠商公開平台 | 否 |
| 本日出工 | Google 試算表（LINE 回報） | 否 |
| 職安新知 | 職安署網站 | 否 |
| 缺失統計 | 雲端 Postgres（填報本來就在雲端） | 否 |
| 無災害／聯絡人／作業循環 | 雲端 board_config | 否 |

真正非內網不可的是**舊版詳細戰情室**那頁（門禁、監視器、成本），那頁
仍由地端主機負責，與本文無關。

## 架構

分成「外部」與「要資料庫」兩半，兩邊各自更新到 Blob，看板讀取時合併。

```
GitHub Actions（每 30 分鐘）                    雲端填報（事件驅動）
  weather.py / worklog.py / osha_news.py          缺失新增/改善/複驗/刪除
  ↓ 用完即丟的 SQLite                              看板設定儲存
  ↓ station / worklog / news / hazards            ↓ refreshBoardCache()
  POST /api/v1/ingest/external                    ↓
  ↓                                                ↓
  Blob: wallboard/external.json        Blob: wallboard/dbsections.json
                    ↘                        ↙
                     GET /api/board-data/{id}
                     （buildBoardData 合併兩份 Blob）
```

### 為什麼這樣切

**省額度。** Netlify 最大的穩態開銷是 Database compute，計費看「資料庫
醒著幾小時」。若排程每 30 分鐘去查一次雲端資料庫，一天會多醒 3~5 小時，
估算 500~750 credits／月，直接爆掉免費的 300（見 docs/雲端額度.md）。

因此：

- **排程只碰外部來源**，完全不碰雲端資料庫。
- **缺失與看板設定改成事件驅動**：填報時資料庫本來就醒著，順手把摘要
  寫進 Blob。沒人填報就不重算，看板讀取只讀 Blob。
- **無災害天數在讀取時算**（純日期運算）。起算日不變、天數每天自然增加，
  所以不需要為了「天數會變」而定期重算。

結論：這套改動對 DB compute 的增量是 **0**。

### 為什麼收集程式沿用 Python、不改寫成 TypeScript

`worklog.py` 的出工解析是 348 行、累積了大量現場真實案例的啟發式規則
（民國日期被打成 `115/ 09 / 0 5`、鋼構廠商把沒出工的班別也列出來、
機具名稱不可計入人數…）。把它改寫成 TS 等於重寫一份會靜默算錯人數的
程式，還要永久維護兩份。**沿用既有 Python，只是換一台永遠開機的機器跑。**

GitHub Actions 對公開 repo 免費且不限分鐘數，正好適合。

## 設定

### GitHub（Settings → Secrets and variables → Actions）

Secrets（機密）:

    WEATHER_API_PASS      氣象站密碼
    WORKLOG_SHEET_URL     出工試算表網址（含人名與 LINE ID）
    CLOUD_INGEST_TOKEN    與雲端 WALL_INGEST_TOKEN 同一組

Variables（非機密）:

    WEATHER_API_URL / WEATHER_API_USER / WEATHER_SITE_MAP
    BUILDING_LABELS       例：BD04:辦公棟,BD05:住宅棟
    PRIMARY_SITE_CODE     例：BD04
    CLOUD_INGEST_URL      https://<站台>/api/v1/ingest/external

專案值一律放 Secrets/Variables，不寫進 workflow YAML——公開 repo 不留
任何工地資訊。

### Netlify

    WALL_INGEST_TOKEN     與 GitHub 的 CLOUD_INGEST_TOKEN 同一組（設為 secret）

## 踩過的坑

**出工試算表要能匿名匯出 CSV。** 程式讀的是
`/export?format=csv`。兩種情況都會回 **401**，而且從網址看不出來：

1. 共用權限不是「知道連結的任何人可以檢視」
2. **檔案被移到垃圾桶**——實際發生過，當時誤判成權限問題調了半天。
   垃圾桶裡的檔案一律 401，不管共用怎麼設。

驗證方式（不必等排程）：

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  "https://docs.google.com/spreadsheets/d/<ID>/export?format=csv"
```

200 才是好的；401 先去 Drive 確認檔案在不在垃圾桶。

**GitHub 只註冊預設分支上的 workflow。** 檔案還在功能分支時，Actions
頁面看不到它、也無法手動觸發，因此**無法在合併前測試 Secrets**。
合併後請立刻手動觸發一次（workflow_dispatch）驗證。

**排程只跑預設分支。** 合併回 main 之前，分支上的 workflow 不會自己跑，
不必擔心測試期間亂推資料。

## 本機驗證

不推上雲端、只印出結果：

```bash
cd backend/onprem && python ../cloud-runner/run_external.py
```

加 `--push` 才會推上雲端（需要 CLOUD_INGEST_URL 與 CLOUD_INGEST_TOKEN）。

## 地端主機還需要嗎

看板已經不需要它。地端主機剩下的職責只有**舊版詳細戰情室**（門禁、
監視器、成本）——那些資料源在公司內網，雲端連不到。若不看那頁，
地端的 push_wallboard 排程可以停掉。
